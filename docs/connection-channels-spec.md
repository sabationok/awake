# Spec: канали зв'язку, довірені пристрої, імена в системі Mac, Web UI

Доповнює [auth-proxy-spec.md](auth-proxy-spec.md). Тут чотири речі: як ми називаємо підключення пристрою, хто в кого
просить дозволи, як прибрати «awake» із системи Mac і як розкласти сторінки «Сервер» і «Web UI» в аппці.

## 1. Хто що знає

| Шар | Що це | Що він знає |
|---|---|---|
| Агент MaControl | бізнес-логіка: модулі, дії, команди | приймає звідусіль: stdin / аппка, Web UI, Telegram. Не знає, яким каналом прийшов запит, знає лише principal і стратегію guard-а |
| Канал зв'язку | localhost, LAN, Tailscale, ngrok, webhooxy, Telegram | просто труба. Нічого не знає про Web UI, про агента чи про те, що через нього ходить |
| Web UI | веб-інтерфейс (раніше «пульт», «дашборд») | показує дерево від агента. Нічого не знає про канал: де його віддають і через що ходять запити, вирішує не він |
| Проксі (Vercel тощо) | сторонній хост, що віддає Web UI і пересилає запити | бере target з Upstash, як у auth-proxy-spec. Про агента і Web UI нічого не знає |

Слово «пульт» у UI і коді прибираємо: це **Web UI** (`Web UI: displayOff` у журналі, джерело сесії `web` → «Web UI»).
Підписи, які прив'язують канал до Web UI, переписуємо: Webhooxy — «Канал зв'язку через relay webhooxy», без «дашборд на
Vercel». Агент — «Бізнес-логіка: дії й команди з Mac, Web UI і Telegram».

## 2. Адреса підключення

Кожен сполучений пристрій і кожна сесія мають адресу:

```
<networkType>:<channel>:<webUiHost>
```

- `networkType`:
  - `local` — пристрій і Mac в одній мережі (фізичній чи приватній), Web UI віддає наш сервер;
  - `remote` — різні мережі, Web UI віддає сторонній хост.
- `channel` — канал зв'язку:
  - для `local`: `localhost`, `lan`, `tailscale`;
  - для `remote`: `webhooxy`, `ngrok`, `tailscale`.
- `webUiHost` — хост, що віддав Web UI: `localhost:47801`, `192.168.1.20:47800`, `mac.tail1234.ts.net`, `<app>.vercel.app`.

Приклади: `local:tailscale:mac.tail1234.ts.net`, `local:lan:192.168.1.20:47800`, `remote:webhooxy:macontrol.vercel.app`.

Агент пише адресу, коли знає її з запиту (порт listener-а, `Tailscale-User-Login`, `Host`, заголовки relay). Що не
знає, пише як `unknown` і UI показує це явно («канал невідомий»), а не ховає.

`lan` я додав сам: це теперішня вкладка «Локально» через Wi-Fi.

### Конфіг Web UI у сховищі (remote)

Сторонній хост Web UI (Next.js serverless proxy) не тримає підписку, тож свій конфіг читає зі сховища (зараз Upstash,
може бути будь-який Redis чи KV). Це аналог Redis pub/sub: модуль gateway публікує останнє значення, а Web UI поки що
читає його на кожен вхід користувача. Детально — «Потім: relay через Vercel» у [auth-proxy-spec.md](auth-proxy-spec.md).

**Gateway, а не агент.** Канали налаштовують модулі gateway, кожен свого виду і лише свої:
- gateway (proxy) — свої проксі: піднімає, видає ключі, публікує конфіг Web UI (`baseUrl` тощо);
- gateway (vpn) — свої приватні мережі, якщо треба (Tailscale serve, вхід у tailnet).

Агент MaControl — бізнес-логіка: він не налаштовує канали і не публікує `baseUrl`. **Агент не знає, чи запит прийшов
через проксі, через VPN чи напряму.** Він знає лише протокол: отримав `http` — відповів по `http`, отримав `ws` — відповів
по `ws`, відкрили `sse` — шле події в `sse`. Чим прийшло, тим пішло. Роути й guard-и одні для всіх.

Хто з провайдерів що доставляє (це знає gateway, не агент):

| Вид | Провайдери | Протоколи до агента |
|---|---|---|
| proxy | webhooxy або інші | `http`, `ws` (режим проксі), `sse` — потім |
| vpn | Tailscale або інші | `http`, `ws`, `sse` |
| напряму | localhost, LAN | `http`, `ws`, `sse` |
| bot | Telegram, Discord, … | оновлення бота: long polling або вебхук |

**Бот через вебхуки.** Оновлення бота — це звичайний вхідний вебхук: провайдер (Telegram) → webhooxy (прийом вебхуків
`queue` | `http` | `ws`) → агент `handleWebhookRequest` → модуль бота `handleWebhook(update)`. Відповідь користувачу
бот шле своїм API (Telegram Bot API), а не у відповідь на вебхук. Через `ws` з webhooxy вебхук приходить так само,
окремим повідомленням, і обробляється тим самим `handleWebhookRequest`.

Приклад. Web UI просить усю статистику одним запитом:
`GET <webhooxyBaseUrl>/api/proxy/api/stats` → webhooxy пересилає запит на Mac по `http` або `ws` → агент отримує
звичайний `GET /api/stats` (з `ws` його розгортає той самий HTTP-застосунок) → guard → контролер статистики → відповідь
тим самим протоколом назад.

Зараз Web UI отримує від webhooxy не proxy-URL, а `/webhooks`. Потрібен окремий роут `/proxy` у webhooxy (запит у
webhooxy: [webhooxy-proxy-request.md](webhooxy-proxy-request.md)).

Що лежить у конфігу (пише gateway, на кожен хост Web UI свій запис):
- `baseUrl` — куди proxy шле запити. Тут і живе канал: relay-кімната webhooxy, адреса ngrok, Tailscale Funnel чи будь-що
  інше. Для proxy це просто URL, тому `remote:webhooxy`, `remote:ngrok` і `remote:tailscale` відрізняються лише цим полем;
- s-to-s `apiKey` (ключ підпису) — proxy підписує ним URL (`X-Proxy-Sign`), і агент знає, що запит прийшов саме від цього
  Next.js serverless proxy;
- `headers` — хедери каналу, які proxy додає наосліп (для webhooxy `X-Relay-Auth`).

Звідси `webUiHost` для `remote`: ключ, яким перевірився `X-Proxy-Sign`, gateway видав конкретному хосту Web UI, тож
хост відомий з ключа, а не з заголовків запиту. `channel` (`proxy:webhooxy`, `vpn:tailscale`, `bot:telegram`) визначає шар gateway / стратегія guard-а, яка
перевірила запит; бізнес-логіка агента адресу лише зберігає й показує, але від неї не залежить. Тунель (ngrok, Funnel) заходить лише на окремий loopback-порт зі своєю стратегією,
як `tailscale`, а не на порт стратегії `local` (див. auth-proxy-spec, «Guard: реєстр стратегій»).

### Зберігання

`devices.via` (`local` | `tailnet`) замінюють три колонки: `network_type`, `channel`, `web_ui_host`. Міграція:
`via='tailnet'` → `local:tailscale:<dnsName з tailscale status або unknown>`, `via='local'` → `local:lan:unknown`.
`web_sessions` бере адресу від свого пристрою; окремо не зберігається.

## 3. Картка «Сполучити пристрій»

- Вкладки — `networkType`: **Локально** і **Дистанційно**. Окремої вкладки «Tailscale» немає: це канал всередині обох.
- Усередині вкладки — вибір каналу (сегменти): Локально — `localhost` / `LAN` / `Tailscale`; Дистанційно — `Webhooxy` /
  `ngrok` / `Tailscale`. Недоступний канал видно сірим з причиною (правило «не ховати, а сірити»).
- Кожен канал має свій QR / URL і свій рядок підказки.
- **Сполучені пристрої — свої в кожній вкладці**: список фільтрується за `networkType`, у рядку видно канал і
  `webUiHost` («Tailscale · mac.tail1234.ts.net»). Пристрій з `unknown` показується з написом «канал невідомий».
- Свічі в Агент → Огляд → «Віддалений доступ» лишаються: вони кажуть, які канали агент взагалі приймає.

## 4. Telegram як канал і вхід

Telegram — ще один канал. Два різні входи:

- **Вхід у бота** — сам бот приймає команди лише від дозволених чатів (зараз `TG_CHAT_ID`). Потім: дозвіл нового чату
  кодом з аппки, як пейринг пристрою.
- **Вхід у Web UI через Telegram** — OAuth-подібний, пристрій отримує сесію лише після «Дозволити» в боті:
  - `oauth`: Web UI → «Увійти через Telegram» → deep link `t.me/<bot>?start=<code>` → бот питає «Дозволити вхід з
    <user agent>?» → Web UI опитує статус → кукі сесії;
  - `qr`: Web UI на іншому пристрої показує QR з тим самим deep link, його сканують телефоном з Telegram.
  
  Код одноразовий і короткий (як у пейрингу). Нова стратегія guard-а не потрібна: результат — та сама сесія
  `web-device`, адреса пристрою отримує `channel` того хоста, звідки відкрили Web UI, а метод входу пишеться окремо
  (`login_method`: `password` | `telegram`).

## 5. Дозволи: два рівні

- **Mac-аппка просить у системи** (macOS): правила sudoers, геолокація, Bluetooth. Видає лише користувач, через системний
  діалог адміністратора, а не через термінал.
- **Модулі просять в аппки**: модуль агента отримує тільки те, що аппка вже має від системи, і лише якщо його увімкнули.

Звідси: **інсталяція пароля не потребує**. `install.sh` не пише sudoers; правило ставить аппка, коли користувач видає
дозвіл у «Дозволах». `uninstall.sh` прибирає правила через той самий шлях (діалог адміністратора).

## 6. Імена в системі Mac

У системі Mac (файли, правила, процеси, команди) — лише MaControl і префікс `mc`. «awake» лишається тільки назвою репо і
доменним модулем «не спати» (`modules/awake`).

| Що | Було | Стане |
|---|---|---|
| sudoers | `/etc/sudoers.d/awake`, `awake-<rule>` | `/etc/sudoers.d/mc-<rule>` (`mc-sleepControl`, `mc-thermalRead`) |
| тимчасові файли правил | `.awake-<rule>.tmp`, `awake-sudoers-*` | `.mc-<rule>.tmp`, `mc-sudoers-*` |
| конфіг | `~/.config/awake/` | `~/.config/macontrol/` |
| база, журнали | `awake.db`, `awake.log`, `agent.log` | `macontrol.db`, `app.log`, `agent.log` |
| аппка | `Awake.app`, bundle `dev.vitalii.awake` | `MaControl.app`, `dev.vitalii.macontrol` |
| команда терміналу | `~/.local/bin/awake` | `~/.local/bin/macontrol` |
| кукі | `mc_device`, `mc_session` | без змін |

Міграція — один раз при старті нової аппки:
1. `~/.config/awake` переноситься в `~/.config/macontrol` (якщо новий не існує), файли перейменовуються; старе
   місце не лишається.
2. Правила `awake-*` і `awake` замінюються на `mc-*` однією дією адміністратора (один системний діалог).
3. UserDefaults зі старого bundle id копіюються в новий.

Ризик зміни bundle id: macOS вважає це новою аппкою, тож дозволи TCC (геолокація, Bluetooth) доведеться видати знову, а
Sparkle-оновлення зі старої версії не прийдуть самі. Bundle id міняємо окремим останнім кроком, після решти перейменувань.

Зовнішні імена (Envify-сервіс `awake-agent`, Vercel `awake-lemon`) — не система Mac; міняються окремо.

## 7. Аппка: «Сервер» і «Web UI»

«Сервер» — сам процес агента, з вкладеними сторінками:
- **Огляд** (observability): стан, uptime, pid, Node / stage, живий журнал, події й помилки;
- **Статистика**: графіки навантаження (теперішні `ServerCharts`);
- **Керування**: старт, зупинка, перезапуск, порти, небезпечна зона.

**Web UI** — окрема сторінка в бічній панелі, бо сервер про Web UI не знає:
- чи пускає взагалі (свіч; вимкнений — сервер не віддає `/app` і не приймає `web-device`);
- що він може показувати: які модулі й сторінки дерева видно у Web UI;
- звідки збірка (опублікована / з аппки, дата), як зараз у секції «Пульт».

## Відкриті питання

- Чи показувати в списку пристроїв метод входу (`password` / `telegram`).
