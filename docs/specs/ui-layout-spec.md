# UI layout: розмітка таблицею вузлів — spec v0.2

Статус: чернетка, ідея погоджена (owner, 2026-11-28). v0.2: ліниве завантаження сторінок і піддерев, кеш GET,
`rev` на сторінку замість одного на все дерево. Код ще не почато. Пара до `app-state-bind-spec.md`:
там значення (AppState, `bind`, `show`), тут структура (які вузли, де і в якому порядку). Звідки береться сторінка —
`ui-routes-spec.md`.

## Шари

| шар | що | як змінюється | чим шлеться |
|---|---|---|---|
| **Shell** | модулі, меню, роути, назви | рідко | `shell` з `shellRev`, завжди одразу |
| **Layout** (цей spec) | вузли сторінки, лейбли, дії, `bind` / `show`, порядок | рідко: модуль увімк. / вимк., новий пристрій у списку | лінивий GET сторінки / піддерева, `layout.patch` з `rev` сторінки |
| **AppState** | значення | часто | `state.full`, `state.patch` з `rev` |
| **Індекс `path → id[]`** | хто читає ключ стейту | будується на клієнті з `bind` / `show` | не шлеться |

Layout не несе значень. Зміна значення ніколи не шле layout.

## Таблиця вузлів

```ts
interface UiNodeRow {
  id: string;              // стабільний між збираннями: 'awake.session.stop', не індекс у масиві
  parentId: string | null; // null лише в кореня
  children: string[];      // порядок дітей; задає його лише батько
  node: UiNodeProps;       // type + пропси, bind, show; без вкладених дітей
}

interface UiLayout {
  shellRev: number;
  pages: Record<string, { rev: string; root: string }>; // лише завантажені сторінки
  nodes: Record<string, UiNodeRow>;                     // лише завантажені рядки
}
```

Структура лишається деревом (у вузла один батько), але клієнт тримає лише його частину: `children` може
посилатися на `id`, рядка якого ще немає в таблиці. Це і є лінива частина, див. «Ліниве завантаження».

- **Джерело правди одне.** Порядок і належність задає `children` батька. `parentId` — похідне поле: сервер
  виставляє його під час нормалізації, клієнт його не редагує, а лише читає (крихти, «секцію з усіма схованими
  дітьми не малюємо», підйом угору).
- **`id` стабільні і унікальні** в межах дерева: `<module>.<page>.<node>`; елемент списку — з ключа даних
  (`nearby.device.<mac>`), не з позиції. Нестабільний id = дифф бачить «усе змінилось».
- **По дроту сторінка іде вкладеним деревом** (`UiPage`, як зараз): його легко читати й дебажити. Клієнт сам
  нормалізує його в `UiLayout`. Патчі вже йдуть за `id`.

## Патчі layout

```ts
type LayoutOp =
  | { op: 'set'; id: string; node: UiNodeProps }                                // пропси вузла, діти ті самі
  | { op: 'insert'; parentId: string; index: number; tree: UiNode }             // піддерево (вкладене)
  | { op: 'remove'; id: string }                                                // разом з піддеревом
  | { op: 'move'; id: string; parentId: string; index: number };

type LayoutMessage =
  | { type: 'layout.patch'; pageId: string; from: string; rev: string; ops: LayoutOp[] }
  | { type: 'layout.stale'; pageId: string; rev: string };   // сторінка змінилась, клієнт її не тримає відкритою
```

- Операції структурні: кожна атомарно оновлює обидва боки (`children` батька і `parentId` дитини). Окремої
  операції «постав `parentId`» немає.
- `rev` сторінки — хеш її нормалізованих рядків. Патч несе `from` (на який `rev` він лягає) і новий `rev`.
  `from` не збігся з тим, що в клієнта, або op на невідомий `id` → клієнт перезавантажує сторінку GET-ом.
- Патч застосовується весь або ніякий: помилка посередині = перезавантаження сторінки.
- Патчі йдуть лише на відкриті сторінки (клієнт каже, які: `layout.watch { pages }`). Решта завантажених отримує
  `layout.stale` → кеш сторінки скидається, наступний візит тягне її заново.

## Ліниве завантаження (owner, 2026-11-28)

Дерево всього застосунку може бути великим, а людина бачить одну сторінку. Тому клієнт не тримає все дерево:
одразу бере лише shell, сторінки й важкі піддерева — коли до них дійшов.

| що | коли | запит |
|---|---|---|
| Shell (модулі, меню, роути з `ui-routes-spec.md`) | підключення | `GET /ui/shell` |
| Сторінка | перехід на неї (або prefetch при наведенні на пункт меню) | `GET /ui/pages/:pageId` |
| Ліниве піддерево (згорнута секція, довгий список) | розгортання / прокрутка до нього | `GET /ui/nodes/:id?depth=1` |

- **Межа ліні — сторінка.** Вона ж роут: сервер будує лише її, а не весь `pages(ctx)` усіх модулів.
- **Вузол-заглушка.** Рядок з `lazy: true` має `children`, але без рядків дітей; клієнт малює скелет і тягне
  піддерево. Сервер ставить `lazy` на секції, які згорнуті за замовчуванням, і на списки довші за поріг.
- **Кеш GET.** Відповідь несе `ETag: "<scope>:<rev>"` і `Cache-Control: private, no-cache`: браузер кешує, але
  щоразу звіряється (`If-None-Match` → `304` без тіла). `max-age` немає, бо layout може змінитись будь-коли;
  `private`, бо в дереві локальні дані. Scope у ETag, щоб Vercel-сторінка не підмінила локальну.
- **Клієнтський кеш** — LRU завантажених сторінок (рядки + `rev`); сторінку, яку давно не відкривали, викидаємо.
- **Mac через `server.sock`** — те саме повідомленнями: `{ type: 'layout.get', pageId, ifRev }` →
  `layout.page` або `layout.notModified`.
- **Vercel / Upstash** — ключ на сторінку (`macontrol:ui:page:<id>`) і `macontrol:ui:shell` замість одного
  `macontrol:ui:tree`; пишеться лише сторінка, чий `rev` змінився. Route handler віддає ETag з ключа.
- **Telegram** уже лінивий: один екран на callback.
- **Стейт не лінивий** (v0.2): AppState малий і шлеться весь. Підписка на гілки стейту по відкритих сторінках —
  відкрите питання.

## Сервер: дифф

Сервер нормалізує нове дерево сторінки і звіряє з попереднім за `id`:

1. `id` зник → `remove`; з'явився → `insert` (найвищий новий вузол піддерева, не кожна дитина).
2. Змінився батько або позиція → `move`.
3. Змінились пропси (без `children`) → `set`.

Відбиток для Upstash (`agent/src/presence/services/ui-sync.service.ts`) рахується так само по вузлах: дерево
пишеться, лише коли дифф не порожній.

## Клієнти

- **Web:** `UiLayout` — гілка того самого стору поза React, що й `appState`. Вузол рендериться за `id`
  (`<NodeById id>` бере рядок і мапить `children`); `set` перемальовує лише цей вузол.
- **Mac:** `@Observable` стор з `[String: UiNodeRow]`; `ForEach(row.children, id: \.self)` дає стабільну
  ідентичність, тож вставка і видалення анімуються самі.

## Застаріле дерево або клієнт (owner, 2026-11-28)

Клієнт, який довго висів (вкладка без перезавантаження, Mac після сну, сесія без виходу), може тримати старий
layout або бути старшим за сервер. Помилка такого роду не показується як збій, а запускає оновлення layout одразу,
кожен клієнт зі свого джерела:

| клієнт | звідки бере layout заново |
|---|---|
| Web на Vercel | `/api/tree` (Upstash) |
| Web локально / через Tailscale | API агента |
| Mac-аппка | сервер через `server.sock` |

Тригери:
- **Невідомий вузол** (`type`, якого рендерер не знає). Web зараз мовчки нічого не малює, Mac робить `.unknown`
  → `EmptyView`. Стає: рендерер кидає `UnsupportedNodeError` → клієнт тягне свіжий layout.
- **Застаріла дія.** Клік несе `pageId` і `rev` сторінки; сервер на дію, якої вже немає, або на старий `rev` відповідає
  кодом `STALE_LAYOUT` (зараз `invalidCommand` / «Unknown action») → клієнт тягне свіжий layout і не показує помилку.
- **Пропущений патч** layout (`from` не збігся) або op на невідомий `id` → сторінка заново GET-ом. (Пропуск `rev` стейту — у
  `app-state-bind-spec.md`.)

Якщо після оновлення вузол усе ще невідомий, старий сам клієнт, а не layout: на місці вузла — заглушка «Онови
аппку» (Mac) / «Онови сторінку» (web, новий бандл), без циклу. Оновлення — не частіше разу на 10 с.

## Перехід

1. Стабільні `id` у всіх вузлах сторінок (зараз частина без `id` або з позиційними).
2. Нормалізація на клієнтах: дерево → `UiLayout`; рендер за `id`. Дерево шлеться як зараз.
3. Shell окремо від сторінок; `GET /ui/shell`, `GET /ui/pages/:pageId` з ETag; сервер будує одну сторінку.
4. Дифф на сервері + `layout.patch` / `layout.stale` по відкритих сторінках; Upstash — ключ на сторінку.
5. `lazy`-вузли і `GET /ui/nodes/:id`.
6. `rev` сторінки в кліках, `STALE_LAYOUT`, `UnsupportedNodeError`.

## Відкриті питання

- Списки (пристрої «Поруч», історія сесій): рядки — це layout (`insert` / `remove`), а значення в рядку — стейт. Чи
  довгі списки (історія) взагалі мають бути вузлами, чи окремим вузлом-списком з даними з пагінованого запиту.
- Vercel-канал: патчі layout через Upstash (журнал ops) чи лише перезавантаження сторінки за ETag.
- Стейт по сторінках: чи підписувати клієнта лише на гілки AppState, які читають відкриті сторінки.
- Поріг «довгого списку» для `lazy` і чи пагінувати піддерево (`?cursor=`).
