# Spec: спільні компоненти дій, форм і статусу (MaControl)

Статус: чернетка для погодження. Код не змінено. Перед кодом змін, що переставляють рядки між сторінками (Telegram > Групи, Web UI > Пароль / Сесії), потрібен мокап у чаті (CLAUDE.md, «Mockup before UI code»).

## 1. Що змінюється і що ні

Одна ідея для всього: **кнопки і меню не малюються руками в сторінці**. Сервер має стан кожного елемента і віддає клієнту опис дій (шаблон). Клієнт тільки малює шаблон і шле клік назад.

Не змінюється: логіка сесій, Telegram, помічник для macOS, сама модель дозволів (`Дозволи` уже працюють за цим принципом і є еталоном).

## 2. Хто чим володіє

- **Сервер** (`agent/`): стан (видано / ні, активна / ні, підключено / ні), набір дій для кожного елемента, умови видимості й варіанту дії, підтвердження, список доступних конекторів. Перевіряє scope (`all | local | mac`).
- **Маніфест конектора** (Telegram): декларує, які дії підтримує для кожного типу сутності (група, тема). Ядро «Групи» читає маніфест і не питає конектор по ходу. Telegram-вкладка показує **тільки** дії, які маніфест віддав.
- **Клієнти** (Web UI, SwiftUI app, Telegram-бот): малюють отриманий шаблон і шлють `UiAction`. Не обчислюють умови, не тримають правила, не пишуть стан.
- **Помічник** (`Helper/`): не змінюється; дії дозволів ідуть через сервер як і раніше.

Правило: кожен елемент UI має одного власника стану (сервер). Клієнт не має «а якщо зараз видано, то покажу» у коді.

## 3. Контракт дії (нове в `contracts/src/ui.ts`)

Зараз `UiButton.variant` = `'filled' | 'plain' | 'destructive'`. Треба:

```ts
type UiActionVariant = 'default' | 'accent' | 'warn' | 'danger';

interface UiMenuItem {
  id: string;
  label: string;
  icon?: UiIcon;                 // SF Symbol, як в iOS; web мапить на Tabler
  variant: UiActionVariant;      // default = сіра, accent = синя, warn = помаранчева, danger = червона
  action: UiAction;
  confirm?: { title: string; text: string; ok: string };  // підтвердження (діалог)
  scope?: UiScope;               // mac-only: видно в web, але вимкнено з підказкою
  hint?: string;                 // «Змінити можна лише в аппці на Mac»
}

interface UiActionSet {
  items: UiMenuItem[];           // сервер уже відфільтрував за станом
}
```

Умови (видано / ні, активна / ні) **сервер обчислює і віддає тільки актуальні пункти**. Для дозволу в стані «видано» прийде один пункт `danger «Відкликати»`; у стані «ні» — один `accent «Запит»`. Клієнт нічого не перевіряє. Джерело стану — timestamp-колонки (`revokedAt`, `disabledAt`), bool лише у відповіді (правило з пам'яті `state-columns-are-timestamps`).

Рендер за кількістю пунктів:
- 1 пункт → кнопка цього варіанту (`accent` / `danger` / `default`).
- 2+ пункти → `DotMenuButton` (кнопка «⋯» праворуч) з таким самим переліком варіантів.
- 0 пунктів → нічого не малюється.

### 3a. Іконки і визначення активного стану

Іконки: `UiMenuItem.icon?: UiIcon` — той самий тип, що вже є в `contracts/src/ui.ts` (`symbol` = назва SF Symbol, `tone`). iOS-меню показує SF Symbol зліва від тексту. Web мапить `symbol` на Tabler (`bell` → `ti-bell`), невідомий символ → без іконки. Колір іконки бере `variant` пункту.

Активне чи ні визначає **сервер**, клієнт не обчислює. Сервер віддає вже розв'язаний список пунктів у UI JSON; клієнт малює те, що отримав.

```ts
function permissionActions(p: { granted: boolean }): UiMenuItem[] {
  return p.granted
    ? [{ id: 'revoke', label: 'Відкликати', variant: 'danger', icon: { symbol: 'xmark.circle', tone: 'red' }, action: { module: 'permissions', name: 'revoke', params: { id: 'temp' } }, confirm: { title: 'Відкликати дозвіл?', text: '…', ok: 'Відкликати' } }]
    : [{ id: 'request', label: 'Запит', variant: 'accent', icon: { symbol: 'hand.raised', tone: 'accent' }, action: { module: 'permissions', name: 'request', params: { id: 'temp' } } }];
}
```

Рішення (27.11): варіант A, оновлення стану через SSE (сервер шле новий розв'язаний вузол). `when` відкладено, не вводимо, поки немає оптимістичного перемикання без сервера.

Варіант B (декларативний `when`, відкладено): сервер віддає пункт з умовою і контекстом, клієнт рахує видимість сам.

```json
{ "ctx": { "status": "active" },
  "items": [
    { "id": "deactivate", "label": "Деактивувати", "variant": "default",
      "when": { "path": "ctx.status", "op": "eq", "value": "active" } },
    { "id": "activate", "label": "Активувати", "variant": "accent",
      "when": { "path": "ctx.status", "op": "eq", "value": "disabled" } }
  ] }
```

Умови обмежені: `op` лише `eq | neq | in`, без виразів і без JS. Одна функція `evaluateWhen` у `contracts/` для web і Swift. Якщо сервер штовхає оновлення стану (SSE), варіант B зайвий: сервер просто шле новий розв'язаний вузол. `when` потрібен тільки там, де клієнт має перемикати стан без запиту на сервер (оптимістичне оновлення). Рекомендація: почати з варіанта A (розв'язаний список), `when` додати пізніше у строго обмеженому вигляді.

Чому так, а не клієнтська умова: одна правда для web, SwiftUI і Telegram-бота; клієнт без стану не може показати застаріле «активне». `granted` сервер виводить із timestamp-колонок (правило `state-columns-are-timestamps`), bool лише у відповіді.

## 4. Спільні компоненти

### 4.1 `ItemCard` (еталон: рядок пристрою і рядок групи)

Структура зверху вниз:
1. **Заголовок** — назва зліва; праворуч `<dot> <status>` (статус словом, наприклад «● Активна», «● Підключено»), якщо елемент має стан; потім `DotMenuButton` або одиночна кнопка дії.
2. **Теги** (опційно) — рядок `Tag`-компонентів між заголовком і коментом, наприклад `Tailscale`.
3. **Коментар** (опційно) — підпис внизу сірим, наприклад «Додав 840457248», «Сполучено 22 лист., 18:53».

Жодних кнопок під заголовком або в рядку коментаря.

### 4.1a Значення тільки для читання (адреса, ключ, ID)

Значення, яке можна лише скопіювати (адреса `https://…ts.net`, ID, маска токена), виводиться **під заголовком рядка**, як коментар, а не праворуч. Праворуч від нього — кнопка «Копіювати» (іконка `copy`, без тексту, з `aria-label`). Після натискання кнопка показує галочку на 1–2 с.

Праворуч у заголовку лишається тільки статус (`<dot> <статус>`) або одна дія / меню. Значення праворуч не ставимо: довгий текст ламає вирівнювання.

### 4.2 `DotMenuButton`

Одна кнопка «⋯» праворуч. Меню: пункти з `UiMenuItem.variant`. `danger` — червоний текст, `warn` — помаранчевий, `accent` — синій, `default` — сірий. Пункт з `scope: 'mac'` у web — видимий, вимкнений, з `hint`.

### 4.2a Референс: меню з open-design-ui

Готовий `DropdownMenu` є в `~/WebstormProjects/open-design-ui/src/molecules/Menu.tsx`. Беремо його для web замість нового меню:
- Модель пунктів `MenuItem` уже покриває нашу: `item` (з `danger`, `disabled`, `icon`, `shortcut`), `separator`, `label`, `sub`, `check`, `radio`.
- `nested="drill"` дає iOS-подібне меню: підрівень виїжджає в ту ж панель з рядком «‹ назва». Для телефонів і вузьких екранів.
- `MENU_LABELS` для всіх рядків (i18n через `labels`).
- Треба додати варіанти `warn` (помаранчевий) і `accent` (синій) поруч із `danger`. Зараз є лише `danger`.
- Preview-меню (`CtxMenu` з lifted preview) відкладаємо до web, як домовились.

Мапінг: `UiMenuItem.variant` → `MenuItem` (`danger` → `danger: true`, `accent` / `warn` → новий клас рядка, `default` → звичайний `item`). Сервер віддає пункти, клієнт передає їх у `DropdownMenu` без логіки.

Swift (`Sources/Features/Remote/UiTree.swift`, SDUI-декодер):
- `UiMenuItem` декодується як `Codable`, нові поля `optional` (правило awake-contract-keeper).
- Меню: SwiftUI `Menu { … } label: { Image(systemName: "ellipsis") }`. Пункт — `Button(role: .destructive)` для danger, `.tint(.accent)` для accent, `Label(title, systemImage: icon.symbol)` для SF Symbol. Розділювач — `Divider()`.
- Підтвердження — `.confirmationDialog` зі `confirm` з JSON.
- Форма: одне поле — `TextField` з Cancel/OK інлайн; два і більше — `.sheet` з `Form`.
- Поточний `UiButton.Variant` у Swift має `filled | plain | destructive` — той самий розрив, що й у contracts; міняємо разом з `ui.ts`.
- Mac-only пункти (`scope: 'mac'`) на Mac активні, у web сірі.

### 4.3 `Tag`

Маленький чіп без дій. Текст і опційно колір (`UiTone`).

### 4.3a Меню — оверлей, не частина верстки

`DotMenuButton` відкриває меню як оверлей (absolute / portal), а не в потоці. Відкрите меню не розсуває картку і не додає порожнього місця. У мокапі від 22.11 меню стояло в потоці, тому картка стала великою; це помилка мокапу, не рішення.

### 4.5a Вибір: сегмент чи дропдаун (правило)

Правило для агента, що пише UI: він сам вибирає між табами / сегментом, дропдауном або адаптивним компонентом. Це не вибір дизайнера під час рендера.

- **Набір статичний** (відомий у коді на етапі збірки: стан, режим, фіксований список): варіантів до 5 включно → таби / сегмент. Більше 5 → статичний дропдаун.
- **Набір динамічний** (приходить із сервера або створений користувачем: групи, топіки, пристрої, будь-які назви): пишеться адаптивний компонент. Він малює таби / сегмент, поки варіантів 5 або менше, і дропдаун, коли їх більше 5. Поріг той самий, що для статичного набору.

Сегмент не має бути з довільними назвами: довга або різна за довжиною назва ламає ширину батона. Тому динамічний набір із довільними назвами завжди ведеться через адаптивний компонент, а не через статичні таби.

### 4.6 `Notice` (сповіщення)

Один компонент для всіх підказок і попереджень. Замінює сіру текстову плашку (наприклад, попередження про Bluetooth).

```ts
interface UiNotice {
  id: string;
  variant: 'info' | 'warn' | 'error';        // info = accent, warn = warning, error = danger
  icon?: UiIcon;
  title?: string;
  text: string;
  sticky?: 'top' | 'bottom';                 // прилип до краю скрол-області; без поля — у потоці
  closable?: boolean;                        // хрестик; закриття пише сервер (dismissedAt)
  once?: boolean;                            // після закриття більше не показувати (ключ id + версія)
  remind?: {
    after: string;                           // ISO 8601 duration: "P1D", "P7D"
    show: 'overlay';                         // v1: оверлей всередині компонента (inline — пізніше)
    title?: string;
    body?: string;
  }[];
}
```

Правила:
- Стан закриття і нагадувань живе на сервері (timestamp), не в клієнті. Клієнт тільки малює і шле «закрити».
- `remind` рахує сервер від `createdAt` або від закриття, клієнт не має таймерів-правил.
- Кольори з токенів: `bg-{role}` + `text-{role}`, без рамок-акцентів з одним боком.
- Нотіфи Mac-only лишаються як є (scope `mac`).

Застосування: підказка про Bluetooth у модулі «Поруч» (variant `warn`: текст попереджає, що без пароля / Apple Watch Mac губиться, тож це попередження, а не нейтральна нотатка; без sticky, без close). Повідомлення про сесію, що втрачає систему, — `error` + sticky bottom.

### 5.8 Модуль «Поруч» (на рівні Awake / Sleeper)

«Поруч» стає окремим модулем у сайдбарі, на тому ж рівні, що Awake і Sleeper. Функціонал у нього свій (Bluetooth-присутність, сполучення поруч), модельно він такий самий: свій манифест, свої налаштування, свій статус.

- Розташування: верхній рівень сайдбару, не вкладений у Web UI.
- Рядок модуля з перемикачем і статусом праворуч, як у Tailscale (5.4-Б).
- Bluetooth-підказка з 4.6 (`warn`) живе всередині модуля.
- Виняток з CLAUDE.md лишається: застосунок поки сканує Bluetooth і шле дані серверу.
- Переставляння рядків сайдбару = мокап у чаті до коду (CLAUDE.md, «Mockup before UI code»).

### 5.5 Web UI > Пароль (окрема вкладка)

### 4.5 `Separator` з опціональним словом

Одна спільна розділова лінія для всіх сторінок (наприклад, авторизація: «email / пароль» → **Or** → кнопки соцмереж).

### 4.4 Форми редагування (інлайн або модалка)

- **Інлайн** — коли полів одне (наприклад, «Пароль Web UI»). Натиснули «Змінити» → поле стає формою з кнопками `Скасувати` / `Зберегти` (порядок: скасувати ліворуч, OK праворуч).
- **Модалка** — коли полів два і більше (наприклад, конфіг Remote KV Store: URL + вибір джерела). Натиснули дію → модалка з тими самими кнопками.
- **Підтвердження видалення** — завжди `ConfirmDialog` з `confirm` з `UiMenuItem`. Не інлайн.

Немає великих окремих кнопок під формою без запиту (наприклад, «Зберегти» зараз виглядає як велика кнопка внизу без команди — прибрати, замість неї форма з Скасувати/OK).

## 5. Сторінки

### 5.1 Telegram > Групи (перенос)

Було: верхній пункт «Групи» з дітьми «Список груп», «Топіки», «Статистика».
Стало: `Telegram` → `Групи` → `Список груп`, `Топіки`, `Статистика`. Ієрархія та іконки Telegram зберігаються.

Рядок групи (`ItemCard`):
- заголовок: назва групи; праворуч `● <status>` (наприклад, «● Активна» / «● Вимкнена»);
- тег(и): за потреби;
- коментар: «Додав <user id>»;
- дії з маніфесту Telegram: `Деактивувати` (стан «активна») або `Активувати` (стан «вимкнена») — `default`; `Вийти з групи` — `danger`, з підтвердженням. Якщо дій два і більше — `DotMenuButton`.

Перенесення — тільки переставити вузол в дереві сайдбару; логіка групи не міняється.

Навігація всередині сторінки «Список груп»: не три списки один під одним, а сегмент (батон-група) або таби з лічильниками: `Активні · 1 | Неактивні · 0 | Запити · 0`. Видно один список за раз, під ним його підпис (наприклад, «Сюди бот публікує сповіщення. Зараз активною може бути одна група.»). Лічильник — частина підпису табу, не окрема секція.

Статистика (Telegram > Групи > Статистика): той самий принцип, що й «Список груп». Не довгий стек блоків, а таби або сегмент з одним видимим блоком за раз. Вміст сторінки статистики в цій сесії не переглядався, тому конкретні таби визначаємо окремо з мокапом. Якщо статистика показує вибір групи, це адаптивний компонент за правилом 4.5a: набір груп динамічний.

Дії в рядку групи: `Деактивувати` (default) і `Вийти з групи` (danger) — два пункти, тож `DotMenuButton`, а не дві кнопки в рядку, як на екрані зараз.

### 5.2 Web UI > Мережі (переробка)

Блоки зверху вниз:

**a) Довірені мережі Wi-Fi.** Один `ItemCard` на мережу з `DotMenuButton`: `Прибрати «<назва>»` — `danger` з `ConfirmDialog`. Під кожним рядком окремої кнопки немає. Коментар футера лишається: «Поза довіреними мережами сервер відповідає тільки цьому Mac. Змінити можна лише в аппці на Mac.»

**b) Remote KV Store** (заміна блоку «Upstash» і блоку «Ключі Upstash (на цьому Mac)»):
- Сегментований вибір **Redis | Upstash** з позначкою `Рекомендовано` на одному з них. Показуються тільки бекенди, для яких сервер має модуль зі стор-адаптером (див. 6).
- Джерело підключення: вкладки **Конфіг | URL**. `Конфіг` — з env / Envify. `URL` — одне поле (connection string).
- Конфіг → сервер створює підключення з конфігу; URL → сервер створює підключення в модулі, що володіє цим бекендом. Клієнт не знає деталей.
- Зміна налаштувань — форма в модалці (2+ поля), кнопки `Скасувати` / `Зберегти`.
- Коментар внизу: «Сюди сервер кладе живий стан для Web UI на Vercel. Історія і журнал лишаються на Mac.»
- Статус у заголовку блоку: `● Підключено` / `● Не підключено` (dot + слово).

**c) Окремо нічого** для REST URL / REST токен — поля прибрати (див. 6, питання про URL).

### 5.3-А Пристрої: канали, фільтр і секції (перебудова, чернетка)

Мокап обов'язковий перед кодом (CLAUDE.md, «Mockup before UI code»). Це переставляння секцій на сторінці, тому мокап показано в чаті до коду.

**Три типи каналів:** `local | priv | proxy`. `localhost` не є каналом.
- `local`: без провайдера, окремого провайдера немає.
- `priv` (приватна мережа): провайдер `tailscale`, далі інші. Авто-вхід: ключ доступний без пароля.
- `proxy`: провайдер `webhooxy`, далі інші. Вхід паролем: ключ розгортається паролем.

Провайдери йдуть нижче типу. Один канал = тип + опційний провайдер.

**Сторінка (зверху вниз):**
1. **Фільтр каналу** — sticky вгорі, не скролиться, два рівні:
   - таби першого рівня: `Local | Priv | Proxy`;
   - якщо у табі один провайдер, під табою не таби, а `SimpleBar` (іконка, назва провайдера, статус `active` праворуч). Підпис про правило входу («Авто-вхід без пароля») іде під заголовком бару, як коментар у нашому компоненті бару, а не під баром. Якщо провайдерів більше, під-таби як описано нижче, а підпис змінюється з табою;
   - у кожної таби свої під-таби (провайдери): `Priv` → `Tailscale` (далі інші); `Proxy` → `Webhooxy` (далі інші); `Local` поки без під-табів (за вашим описом провайдера немає). Під-таби змінюються разом з табою, тобто набір не спільний.
   - Під фільтром рядок правил типу: «авто-вхід» або «вхід паролем».
2. **Сполучити новий** — QR і текст для обраного каналу. Перший, бо це головна дія сторінки.
3. **Сполучені пристрої** — фільтруються за обраним каналом. Не бейдж, а фільтр: пристрої інших каналів не показуються.
4. **Запити на сполучення** — внизу, фільтруються за тим самим каналом.

Одна сторінка, а не окремі вкладки: вибір каналу зверху керує всіма секціями, тож перемикання миттєве і без переходів.

**Відкрите:** для `local` авто-вхід не визначено. Ви писали авто-вхід лише для приватної мережі, тому поки вважаю його без авто-входу (як `proxy`). Підтвердіть.

### 5.4-Б Модуль Tailscale (налаштування модуля)

Модуль знає тільки про себе: увімкнути / вимкнути, адреса в tailnet, опис того, що робить. Web UI, сесії, вкладки Agent тут не згадуються: модуль не знає про Web UI (Web UI статичний, запити йдуть до сервера, модулю це байдуже).

- Рядок модуля: `Увімкнено` (перемикач), коментар «Приватна мережа tailnet: доступ з твоїх пристроїв з будь-якої мережі». Статус `● Працює` / `● Вимкнено` праворуч, а не під заголовком.
- Рядок `Адреса`: значення праворуч (`https://…ts.net`), копіювання — дія меню.
- Футер-опис: лише про сам модуль (що він робить, як вимкнути). Без згадок інших модулів і правил «коли працює».

Статус «Web UI через Tailscale працює» з екрана прибираємо: це не стан модуля Tailscale.

### 5.10 Групи: налаштування групи і конектор (розділити)

З екрана: у одному списку змішано налаштування групи і опис конектора. Розділяємо за власником:

**Налаштування групи** (модуль «Групи», перемикачі й вибори, пишуть стан):
- `Куди слати сповіщення` — вибір (`Група` / `Приватний чат`), підпис: «Поки публікацію не дозволено в жодну групу, сповіщення йдуть у приватний чат».
- Налаштування провайдера (`Запасний приватний чат`, `Команди в групі`) не належать ядру груп. Вони живуть на вузлі `Telegram` (див. нижче).
- Футер: «Запасний приватний чат спрацьовує, коли відправка в групу не вдалась. Якщо групи немає зовсім, сповіщення йдуть у приватний чат завжди.»

**Конектор Telegram** (тільки читання, з маніфесту): які можливості підтримує провайдер. Тобто `Топіки на джерело`, `Команди (підтримка)`, `Закріплення`, `Запрошення`, `Учасники`, `Заявки на вступ` зі значеннями `є` / `немає` і підписом про підтримку. Перемикачі тут не потрібні. Футер: ліміт провайдера (20 повідомлень на хвилину в одну групу).

Дубль знято: перемикач `Команди в групі` (дозвіл, на вузлі `Telegram`) і рядок конектора `Команди (підтримка)` (можливість, тільки читання) мають різні назви і різні місця.

Ієрархія (рішення):
- `Telegram` — верхній вузол: можливості конектора (read-only, з маніфесту) і загальні налаштування бота.
- `Telegram > Команди` — команди приватного чату з ботом (вузол, не окремий розділ модуля «Групи»). У групах і топіках команд бота немає, крім власних команд топіка (5.9).
- `Telegram > Групи` — налаштування групи (`Куди слати`, `Запасний чат`, `Команди в групі`) і вкладки `Список груп | Топіки | Статистика`.

Можливості конектора живуть на вузлі Telegram, не в групі.

**Маршрутизація сповіщень (одне правило, тут і лише тут):** поки публікацію не дозволено в жодну групу, сповіщення йдуть у приватний чат. Топік з вимкненим перемикачем пише в General групи; джерела, що шлють скрипт Mac, пишуть у приватний чат. Вимкнення не видаляє топік у групі.

**Команди** — вузол `Telegram > Команди`: команди бота, загальні для всіх груп і топіків. Команди окремого топіка задаються в його рядку (5.9), а не тут.

Рішення власника (замінює попереднє «додаються»): команди бота для приватного чату з ботом — це меню «/» для private. У групі команд немає: у General їх немає, меню «/» групи порожнє (`BotCommandScope all_group_chats = []`). Кожен топік має лише свої команди; команди приватного чату в топіках не працюють. Бот сам фільтрує за `message_thread_id` і тримає в кожному топіку закріплене повідомлення зі списком його команд (меню «/» на топік Telegram не дає). В UI у списку команд топіка загальні сірими **не** показуються.

Групи — провайдер-нейтральне ядро (`contracts/src/groups.ts`, `GroupProviderId`): будь-який провайдер підставляється в нього через маніфест. Telegram — перший провайдер. У сайдбарі вузол «Групи» — перший рівень вкладеності під `Telegram`, з дочірніми `Список груп`, `Топіки`, `Статистика`, як зараз.

### 5.11 Сповіщення: без окремого табу «Попередження»

З екрана: сторінка «Сповіщення» має таби по модулях (Sleeper, Стан Mac, Tailscale, Awake, Агент, Групи) і ще один таб «Попередження» зі спільними перемикачами `Сесія Awake скоро скінчиться`, `Sleeper скоро спрацює` та `Попередити за 15 хв`.

Рішення:
- Таба «Попередження» немає. Кожне сповіщення належить своєму модулю.
- Перемикач «Сесія Awake скоро скінчиться» і `Попередити за N хв` живуть на сторінці модуля Awake, перемикач «Sleeper скоро спрацює» — на сторінці Sleeper. Так само для всіх модулів.
- Рядок-футер «Модулі реєструють свої події самі…» — пояснення для розробника, з UI прибираємо.
- Загальних налаштувань сповіщень немає. Якщо з'явиться спільне (наприклад, тихий режим), воно окремою секцією, а не табом.

Чому скаче (зі скріну): рядок табів з 7+ елементів вилазить за ширину вікна, тому при виборі таба контент зсувається (обрізаний текст «…бота забрали права»). Це не лікується шириною: з 5.11 рядок табів зникає, кожен модуль має свої сповіщення на своїй сторінці. Поки таби лишаються, рядок має фіксовану ширину з горизонтальним скролом і не зсуває контент.

Загальне правило: таби і фільтри — окрема плашка (власна поверхня з відступом і роздільником), візуально відокремлена від контенту. Не просто рядок над списком. Ця плашка sticky, коли сторінка скролиться (як фільтр каналів у Пристроях, 5.3-А).

Вузол «Сповіщення» під `Telegram` (зараз відкритий на скріні): усі події на ньому стосуються самого бота (`Публікацію в групу дозволено`, `Бот вийшов з групи`, `У бота забрали права в групі`, `Бота видалили з групи`, `Сповіщення не дійшло в групу`). Тому вони переїжджають на вузол `Telegram` (події бота), а не в `Групи`. Перенесення — після мокапу.

### 5.9 Telegram > Групи > Топіки

Проблема з екрана: кожен топік у своїй секції з заголовком, своєю карткою і своєю кнопкою «Створити заново». Одна плашка на секцію без сенсу.

Нова форма:
- **Один блок** зі списком усіх топіків. Заголовка на кожен топік немає.
- Рядок топіка: назва зліва, коментар під нею (наприклад, «Sleeper · активний · шле скрипт Mac»), праворуч **перемикач «публікувати»**. Перемикач і є індикатор активності, окремого статусу немає.
- Команди топіка: пункт `Команди` у `DotMenuButton` рядка (або окремий перемикач, якщо їх мало). Відкриває список команд, які бот приймає в цьому топіку. Команди топіка — лише його власні (рішення 5.10). Загальні команди бота сюди не входять і в списку топіка не показуються. Бот тримає в топіку закріплене повідомлення з його командами.
- Дії рядка в `DotMenuButton`: `Команди`, `Видалити` (danger). Підтвердження має сказати, що топік видаляється в групі Telegram і це незворотно. Окрема кнопка під рядком не малюється.
- `Створити заново` з'являється лише тоді, коли топіка немає в Telegram. Це стан з сервера (пункт `create`, що приходить тільки при відсутньому топіку), а не постійна кнопка.
- **Створити топік** — окрема дія блоку (кнопка «Створити» в шапці блоку або пункт меню блоку), відкриває форму. Форма: назва топіка, одне поле → інлайн; якщо полів більше — модалка (правило 4.4).
- Перемикач лише про публікацію. Вмикання / вимикання не має інших наслідків на UI.

Додатково:
- Вибір групи: зверху sticky, адаптивний компонент за 4.5a (набір динамічний). Поки груп 5 або менше, це таби / сегмент; від 6 — дропдаун з стрілкою ▾ і назвою вибраної групи. Під ним показується блок топіків вибраної групи. Не картка над топіками і не сегмент.
- Статус групи «Топіки можна створювати» праворуч від назви групи в шапці блоку, як скрізь, а не під назвою.
- Назва модуля-джерела (наприклад «Sleeper») не стає заголовком секції. Вона лише назва рядка топіка, тому заголовок «Sleeper» прибираємо.
- Футер блоку: «Вимкнення не видаляє топік у групі.» Правило маршрутизації записане в 5.10, тут не дублюємо.

Реєстрація топіків: кожен модуль додає свої топіки через свій маніфест, так само як команди. Використовуємо той самий механізм реєстрації, що вже є для команд; окремого списку топіків у коді немає.

## 6. Питання про Remote KV Store (треба рішення)

1. **URL замість URL + токен.** Redis-URL (`rediss://default:<token>@host:port`) містить креденшіали, тому одного поля досить. Upstash REST (`https://…upstash.io` + токен) одним полем не обійтися. Пропоную: варіант URL приймає connection string; REST-пару залишити тільки в конфізі. Потрібне рішення.
2. **Web-сумісність — не блокер.** Redis по TCP уже використовується server-side на serverless, тому окремий прапорець `webCompatible` не потрібен. Вибір бекенда визначає лише наявність стор-адаптера на сервері.
3. **Де живуть ключі — вирішено.** Якщо Envify доступний — секрети беруться з Envify (конфіг-варіант). Якщо ні — підключення зберігаються на Mac у SQLite, зашифровані, як рядки таблиці `connections`:

   ```
   slug            text pk            e.g. remote_kv_store.main
   type            text               remote_kv_store | …
   provider        text               redis | upstash | …
   v               int                версія схеми значень
   securedFields   text[]             імена полів, що шифруються, e.g. ['privateKey']
   values          json               { privateKey?: …, url?: … } — securedFields зашифровані
   disabledAt      timestamp | null   стан — timestamp, не bool (правило state-columns)
   ```

   Ключ шифрування не лежить у тій самій БД: окремо, у Keychain або `~/.config/awake` з правами 600. Інакше шифрування нічого не дає.

   Контракт для UI: сервер віддає `values` з замаскованими `securedFields` (показує «•••• задано»), значення не йде назад у клієнт; клієнт шле лише нові значення на запис.

4. Сервер: шаблони дій для Дозволів, Пристроїв, Груп, Довірених мереж, Паролю, Сесій; Remote KV Store як вибір бекенда + джерело.
5. Swift-рендерер тих самих компонентів.
6. Перевірка: кожен рядок має рівно одну дію або меню; дозвіл «видано» показує лише `danger`; mac-only дії вимкнені у web з підказкою.

## 9a. Модель довіри Web ↔ Mac (рішення)

- Секрети (connection strings, токени, пароль, ключ K) на web не потрапляють ніколи.
- Для кожної web-сесії Mac генерує сесійний HMAC-ключ `S`.
- `S` обгорнутий ключем з пароля (Argon2id, варіант A). Web при вході розгортає `S` паролем, пароль стирає, `S` живе тільки в пам'яті вкладки.
- Callback-и: тіло + `ts` + `nonce` + `HMAC(S)`. Сервер приймає вікно ±N хв, nonce кешується на це вікно, повтори відкидаються.
- Завершення сесії (кнопка `Завершити` у «Сесіях», 5.6) = Mac відкликає `S` (`revokedAt` timestamp). Web більше не може підписувати, без окремого розлогіну.
- Без `S` web бачить лише статус без значень: «задано / не задано», маска «•••• задано», timestamp-и. Дії зміни вимкнені (сірі, видимі) з підказкою «розблокуйте сесію». Сервер теж відхиляє такі дії без валідного підпису: вимкнена кнопка лише UX, не захист.
- Шифрування каналу не потрібне для callback-ів, бо в них немає секретів. Mac передає wrapped `S` тільки після того, як сесія створена (вхід на web). До входу на relay нічого з ключами не лежить.

## 10. Відкриті питання

- Ваша ідея альтернативи «довіреній мережі». Не описана в повідомленні, тому в спеці її немає.
- Рішення щодо 6.1 (URL vs connection string для Upstash) і 6.2 (web-сумісність). 6.3 вирішено: Envify, інакше SQLite на Mac з шифруванням.
- Джерело ключа шифрування: Keychain чи файл у `~/.config/awake`.
- Попередній мокап Web UI, на який посилалась основна сесія, мені не відомий у цій сесії. Розбіжності перевірю з ним, якщо він у `docs/` або в чаті.
